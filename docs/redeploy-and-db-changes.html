Redeploying Code & Database Changes

What steps to run for a code change vs a DB change — and exactly what happens to your live data when you deploy a new JAR.

The one-line answer. Deploying a new JAR does not wipe or reset your database. Your tables and rows are stored in MySQL / RDS, not inside the app. On startup the app runs Flyway, which only applies new migration files it hasn't seen yet and never re-runs old ones. Hibernate is set to ddl-auto: validate, so it checks the schema matches the code but never changes data. Existing orders, customers, products, leads — all preserved across redeploys.

1 How the app treats your data (the model)

Three pieces decide what happens on every deploy. Understanding them removes all the guesswork:

PieceSettingWhat it means for your data
Where data livesMySQL / RDS on diskThe database is a separate process from the app. Replacing the JAR never touches the data files.
Flyway migrationsspring.flyway.enabled: true, baseline-on-migrate: true, files in db/migrationOn startup Flyway looks at the flyway_schema_history table, sees which V1…Vnn scripts already ran, and applies only the new ones. Already-applied scripts are skipped forever.
Hibernate DDLddl-auto: validateHibernate only verifies the tables match the entity classes. It will never create, drop, or alter tables or delete rows. If the schema doesn't match, the app refuses to start (a safe fail).
Bottom line: the schema is owned by your versioned SQL migrations, not by the app auto-magically. That's exactly why redeploys are safe and predictable.

2 Which kind of change am I making?

Your changePathData impact
Java logic, bug fix, new endpoint, Angular UI change — no schema changePath A (§3)Zero data untouched
New table / column / index, or a data backfillPath B (§4)Additive your new migration runs once

Not sure? If you didn't add a file under backend/src/main/resources/db/migration/, it's a code-only change (Path A).

3 Path A — Code-only change (no DB change)

Backend logic, a new API, or a frontend tweak. Nothing about the database changes.

On your PC — build the artifacts

# Backend JAR
cd "c:\E Drive\Shifa-Software\backend"
mvn -DskipTests package        # produces target\shifa-oms-*.jar

# Admin UI (only if you changed the frontend)
cd "c:\E Drive\Shifa-Software\frontend"
npm ci
npx ng build admin --configuration production --base-href /

Upload to the server

scp -i "C:\path\to\shifa-key.pem" "..\backend\target\shifa-oms-0.0.1-SNAPSHOT.jar" ubuntu@<PUBLIC_IP>:/home/ubuntu/shifa-oms.jar
# frontend only if rebuilt:
scp -i "C:\path\to\shifa-key.pem" -r ".\dist\admin\browser\*" ubuntu@<PUBLIC_IP>:/home/ubuntu/admin-dist

On the server — swap in & restart

sudo cp ~/shifa-oms.jar /opt/shifa/shifa-oms.jar && sudo chown shifa:shifa /opt/shifa/shifa-oms.jar
# frontend only if rebuilt:
sudo rm -rf /var/www/shifa/admin/* && sudo cp -r ~/admin-dist/* /var/www/shifa/admin/
sudo chown -R www-data:www-data /var/www/shifa

sudo systemctl restart shifa-oms && sudo systemctl reload nginx
sudo journalctl -u shifa-oms -f       # watch for "Started Application" / "Tomcat started on port 8080"
Data impact: none. Flyway sees no new migrations and does nothing to the schema; Hibernate validates and starts. Every existing row is exactly as it was.

4 Path B — Database change (add a new migration)

Golden rule: never edit a migration that has already run. Flyway stores a checksum of every applied script; changing V1…V27 after they've run makes the app fail to start with a "checksum mismatch". To change the schema, always add the next new file.

Step 1 — create the next versioned file

The highest existing version is V27, so your next file is V28__short_description.sql in backend/src/main/resources/db/migration/. Use the next number each time (V29, V30…).

-- V28__add_customer_notes.sql   (additive = safe)
ALTER TABLE customers ADD COLUMN notes VARCHAR(500) NULL;
CREATE INDEX ix_customers_created_at ON customers (created_at);
Prefer additive, nullable changes. Adding a nullable column or a new table/index doesn't touch existing rows. If you must add a NOT NULL column, give it a DEFAULT or backfill in the same script so existing rows stay valid (Hibernate's validate will reject a mismatch on startup).

Step 2 — if you touch an entity, update the Java too

Because ddl-auto: validate compares entities to the schema, a new mapped column needs both the migration and the matching JPA field. Add a column the entities don't map? Fine — validate ignores extra unmapped columns. Map a field with no column? Startup fails. Keep them in sync.

Step 3 — build, upload, restart (same as Path A)

Rebuild the JAR (the new V28 file is bundled inside it), scp it up, and restart the service. On startup Flyway detects V28 is new, runs it once, records it in flyway_schema_history, and the app starts.

sudo cp ~/shifa-oms.jar /opt/shifa/shifa-oms.jar && sudo chown shifa:shifa /opt/shifa/shifa-oms.jar
sudo systemctl restart shifa-oms
sudo journalctl -u shifa-oms -f   # look for "Migrating schema ... to version 28"
Data impact: only what your V28 script does. Additive scripts preserve all existing rows; a destructive script (drop/rename/delete) does exactly what you wrote — which is why §6 (back up first) matters here.

5 What happens to data on re-run — every scenario

You do thisWhat Flyway / Hibernate doesYour data
Redeploy the same JAR (restart)No new migrations; validate passesUnchanged
Deploy a JAR with only code changesNo new migrations; validate passesUnchanged
Deploy a JAR with a new additive migration (V28 add column/table)Runs V28 once, records itPreserved + new empty column/table
Deploy a JAR with a destructive migration (drop/rename/DELETE)Runs it once, as writtenChanges as scripted — back up first
You edited an already-applied V1–V27 fileChecksum mismatch → app won't startUntouched but app is down until reverted
You restore an old dump over the live DBOverwrites everythingReplaced — never do this on live data
Rebuilding the JAR does not reset the database. A "fresh" reset only happens if you point the app at an empty database (or drop the schema yourself). As long as you keep pointing at the same shifa_dashboard / RDS instance, your data carries over every deploy.

6 Always back up before a deploy (especially Path B)

For code-only deploys a backup is optional; for any schema/data change, take one first. You have three options:

a) The app's own nightly backup (automatic)

The backend already runs mysqldump --single-transaction every night at 02:00 (app.backup.cron), gzips it, and stores it. Good safety net, but it's yesterday's data — take a fresh one before a risky change.

b) Manual dump on the server (works for local MySQL and RDS)

# local MySQL on the EC2:
mysqldump -u shifa -p --single-transaction shifa_dashboard > ~/shifa_$(date +%F_%H%M).sql
# RDS (point host at the endpoint):
mysqldump -h <rds-endpoint> -u shifa -p --single-transaction shifa_dashboard > ~/shifa_$(date +%F_%H%M).sql

c) RDS snapshot (managed DB only) recommended before schema changes

Console → RDS → your instance → Actions → Take snapshot, or by CLI. A snapshot is a full point-in-time restore point:

aws rds create-db-snapshot --region ap-south-1 \
  --db-instance-identifier shifa-mysql \
  --db-snapshot-identifier shifa-before-v28-$(date +%Y%m%d-%H%M)
Restore creates a new RDS instance from the snapshot; you then repoint DB_HOST in /etc/shifa/shifa.env. RDS also keeps automated backups (point-in-time restore) for the retention window you set.

7 The seed migrations (V22 / V27) — production warning

Two migrations insert demo/test data: V22 (demo dataset) and V27 (large NOW()-relative test seed). They run automatically on a fresh DB and are perfect for a client demo.

For a clean production database with no fake rows, decide this before first launch: either remove V22/V27 from the build, or start from an empty DB and enter real data through the admin UI. Once these have run on a database, don't delete the files afterward — that triggers Flyway's "missing migration" check. Removing them only makes sense for a brand-new environment.

8 Rollback if a deploy goes wrong

ProblemFix
New code is buggy, no migration was addedCopy the previous JAR back to /opt/shifa/shifa-oms.jar and restart. Data was never touched.
App won't start after editing an old migrationRevert that file to its original content, rebuild, redeploy. (Never edit applied migrations.)
A migration ran but the new code is badRoll the code back to the previous JAR. The additive schema change is harmless to old code (extra columns/tables are ignored).
A destructive migration lost dataRestore from your pre-deploy dump / RDS snapshot (§6), then repoint DB_HOST if you restored to a new instance.
Tip: keep the last known-good JAR on the server (e.g. ~/shifa-oms.prev.jar) so rollback is a one-line copy + restart.

10 Copy-paste cheat sheet

Code-only redeploy

mvn -f "backend/pom.xml" -DskipTests package
scp -i key.pem backend\target\shifa-oms-*.jar ubuntu@HOST:/home/ubuntu/shifa-oms.jar
ssh: sudo cp ~/shifa-oms.jar /opt/shifa/shifa-oms.jar && sudo systemctl restart shifa-oms

Database change

1. add backend/src/main/resources/db/migration/V28__desc.sql   (never edit V1..V27)
2. (RDS) aws rds create-db-snapshot ... shifa-before-v28-...    (back up first)
3. mvn -f "backend/pom.xml" -DskipTests package   (new migration is inside the JAR)
4. scp up + sudo systemctl restart shifa-oms
5. sudo journalctl -u shifa-oms -f   -> "Migrating schema ... to version 28"
Remember: new JAR ≠ new database. Your data lives in MySQL/RDS and survives every deploy. Flyway only adds what's new; Hibernate only checks. Back up before any schema change, keep migrations append-only, and you can redeploy as often as you like with confidence.
