Fresh AWS Free-Tier Instance — Setup Runbook

Stand up the exact same application on a brand-new EC2 instance in the new account (Admin-Weblithic · 226635093151), storage on S3, kept within the 12-month Free Tier. The current live box is left completely untouched.

Before you start — what stays free. The only things that cost money if you're not careful are the instance size, an idle/second public IP, and going beyond the Free-Tier limits. Follow the sizes in this guide (t3.micro/t2.micro, one 30 GB disk, one Elastic IP kept attached to the running instance) and you stay at roughly ₹0 for the first 12 months. S3 for attachments is a few MB → well inside the 5 GB free allowance.

2. Allocate & attach an Elastic IP

A plain instance’s public IP changes every stop/start. An Elastic IP gives you a permanent address and is free while attached to a running instance (covered by the 12-month public-IPv4 Free-Tier hours).

  1. EC2 → Elastic IPs → Allocate Elastic IP address → Allocate.
  2. Select it → Actions → Associate → choose your instance → Associate.
Avoid charges: you’re billed for an Elastic IP only if it’s not attached to a running instance, if you keep it on a stopped instance, or if you allocate a second one. Rule: one Elastic IP, attached, instance kept running. If you ever terminate the instance, release the Elastic IP too.

From here on, <ELASTIC_IP> means the address you just allocated.

3. Create the S3 bucket + IAM role (attachments / profile images / payment screenshots)

The app stores payment screenshots, profile/ID images, and internal label PDFs in S3 (durable, off the server disk).

3a. Create the bucket

  • Console → S3 → Create bucket. Name e.g. shifa-oms-files-prod (globally unique — add a suffix if taken).
  • Region: same as the instance (e.g. ap-south-1).
  • Keep “Block all public access” = ON (the app reads/writes it privately via the IAM role — files are never public).

3b. Create an IAM role for the instance

  • Console → IAM → Roles → Create role → Trusted entity AWS service → EC2.
  • Skip attaching managed policies; create the role (e.g. shifa-ec2-role), then add an inline policy (replace the bucket name):
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ShifaBucketObjects",
      "Effect": "Allow",
      "Action": ["s3:PutObject","s3:GetObject","s3:DeleteObject"],
      "Resource": "arn:aws:s3:::shifa-oms-files-prod/*"
    },
    {
      "Sid": "ShifaBucketList",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::shifa-oms-files-prod"
    }
  ]
}

3c. Attach the role to the instance

EC2 → select instance → Actions → Security → Modify IAM role → choose shifa-ec2-role → Update. Because the instance uses the role, you leave the access/secret keys blank in the env file (most secure).

S3 cost: Free Tier includes 5 GB storage + 20k GET + 2k PUT/month for 12 months. Screenshots/PDFs are tiny, so this is effectively free. (If you’d rather avoid S3 entirely, set STORAGE_PROVIDER=DB in Step 8 to keep files inside MySQL — but you asked for S3, so we use S3.)

4. Connect over SSH (from Windows)

Windows refuses a key that’s too open. Lock the .pem permissions once, then connect:

:: Run in Command Prompt / PowerShell (adjust the path to your .pem)
icacls "C:\Users\Parul\Downloads\shifa-newbox.pem" /inheritance:r
icacls "C:\Users\Parul\Downloads\shifa-newbox.pem" /grant:r "%USERNAME%:R"

:: Connect (Ubuntu default user is "ubuntu")
ssh -i "C:\Users\Parul\Downloads\shifa-newbox.pem" ubuntu@<ELASTIC_IP>

Accept the host-key prompt the first time. You’re now on the server; run the following steps there.

Keep the SSH inbound rule limited to your IP. If your IP changes and you can’t connect, update that rule (or use EC2 → Connect → EC2 Instance Connect in the browser).

5. Add a swap file (important on 1 GB RAM)

t3.micro has 1 GB RAM; MySQL + the JVM together need a cushion. A 2 GB swap file prevents out-of-memory kills:

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h        # confirm "Swap: 2.0Gi"

6. Install Java 21, MySQL 8, Nginx

sudo apt-get update && sudo apt-get upgrade -y
sudo apt-get install -y openjdk-21-jre-headless mysql-server nginx unzip

java -version          # expect openjdk 21.x
systemctl status mysql --no-pager | head -3
nginx -v
The backend is built for Java 21. Ubuntu 24.04 ships OpenJDK 21 in its repos (used above). On 22.04, openjdk-21-jre-headless is also available; if not, use Amazon Corretto 21.

7. Create the database + app user

Pick a strong DB password and use it consistently in Step 8.

sudo mysql <<'SQL'
CREATE DATABASE IF NOT EXISTS shifa_dashboard
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS 'shifa'@'localhost'
  IDENTIFIED BY 'CHANGE_ME_STRONG_DB_PASSWORD';
GRANT ALL PRIVILEGES ON shifa_dashboard.* TO 'shifa'@'localhost';
FLUSH PRIVILEGES;
SQL
GRANT ALL on the one schema gives Flyway the rights it needs to create tables on first boot. MySQL listens on localhost only (not exposed to the internet) — good.

8. Create the app user, folders & the environment file

sudo useradd -r -s /usr/sbin/nologin shifa 2>/dev/null || true
sudo mkdir -p /opt/shifa /var/www/shifa/admin /etc/shifa
sudo chown -R shifa:shifa /opt/shifa

# Generate a strong JWT secret and note it down:
openssl rand -base64 48

Create /etc/shifa/shifa.env (root-owned, mode 600). Fill in the DB password, the JWT secret from above, and your S3 bucket:

sudo tee /etc/shifa/shifa.env >/dev/null <<'ENV'
SPRING_PROFILES_ACTIVE=prod

# --- Database (local MySQL) ---
DB_HOST=localhost
DB_PORT=3306
DB_NAME=shifa_dashboard
DB_USERNAME=shifa
DB_PASSWORD=CHANGE_ME_STRONG_DB_PASSWORD
DB_POOL_SIZE=10

# --- Security ---
JWT_SECRET=PASTE_THE_openssl_rand_OUTPUT_HERE

# --- File storage on S3 (uses the instance IAM role; keys stay blank) ---
STORAGE_PROVIDER=S3
STORAGE_S3_BUCKET=shifa-oms-files-prod
STORAGE_S3_REGION=ap-south-1
STORAGE_S3_PREFIX=
STORAGE_S3_ACCESS_KEY=
STORAGE_S3_SECRET_KEY=
STORAGE_S3_ENDPOINT=

# --- Uploads (phone screenshots are 2-5 MB) ---
MAX_UPLOAD_FILE_SIZE=10MB
MAX_UPLOAD_REQUEST_SIZE=12MB

# --- Integrations: keep mocked until the client provides live creds ---
PAYMENT_MODE=SANDBOX
COURIER_MODE=MOCK
WHATSAPP_MODE=MOCK
MAIL_MODE=MOCK
QUIKSHIPX_ENABLED=false
QUIKSHIPX_MODE=MOCK

# --- Backups (nightly mysqldump) ---
MYSQLDUMP_PATH=mysqldump
BACKUP_CRON=0 0 2 * * *

# --- JVM tuning for a 1 GB free-tier VM ---
JAVA_OPTS=-Xms256m -Xmx640m -XX:+UseSerialGC
ENV

sudo chmod 600 /etc/shifa/shifa.env
sudo chown root:root /etc/shifa/shifa.env
Do not commit this file to git — it holds real secrets. On a 1 GB box keep -Xmx ≤ ~640–768 MB so MySQL has room.

9. Install the systemd service

sudo tee /etc/systemd/system/shifa-oms.service >/dev/null <<'UNIT'
[Unit]
Description=Shifa Herbal Remedies OMS (Spring Boot)
After=network.target mysql.service
Wants=mysql.service

[Service]
Type=simple
User=shifa
Group=shifa
EnvironmentFile=/etc/shifa/shifa.env
WorkingDirectory=/opt/shifa
ExecStart=/bin/sh -c '/usr/bin/java $JAVA_OPTS -jar /opt/shifa/shifa-oms.jar'
SuccessExitStatus=143
Restart=on-failure
RestartSec=5
NoNewPrivileges=true
ProtectSystem=full

[Install]
WantedBy=multi-user.target
UNIT

sudo systemctl daemon-reload
sudo systemctl enable shifa-oms      # start on boot (we start it in Step 12, after the JAR is uploaded)

10. Configure Nginx (serves the admin panel + proxies the API)

sudo tee /etc/nginx/sites-available/shifa >/dev/null <<'NGINX'
server {
    listen 80;
    listen [::]:80;
    server_name _;                 # replace with your domain later
    client_max_body_size 15m;
    gzip on;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }

    location = /api/admin/events {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Connection '';
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
    }

    location / {
        root /var/www/shifa/admin;
        try_files $uri $uri/ /index.html;
    }
}
NGINX

sudo ln -sf /etc/nginx/sites-available/shifa /etc/nginx/sites-enabled/shifa
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

11. Build the app locally & upload it

Run these on your Windows dev machine (in the project folder), then upload the two artifacts.

:: 1) Backend fat JAR
mvn -f backend/pom.xml -DskipTests clean package
::   -> backend\target\shifa-oms-0.0.1-SNAPSHOT.jar

:: 2) Admin web bundle (base-href /)
npm --prefix frontend run build:admin
::   -> frontend\dist\admin\browser\

:: 3) Upload both to the server (home dir first)
scp -i "C:\path\shifa-newbox.pem" backend\target\shifa-oms-0.0.1-SNAPSHOT.jar ubuntu@<ELASTIC_IP>:~/shifa-oms.jar
scp -i "C:\path\shifa-newbox.pem" -r frontend\dist\admin\browser ubuntu@<ELASTIC_IP>:~/admin-dist

Then on the server, move them into place:

sudo cp ~/shifa-oms.jar /opt/shifa/shifa-oms.jar
sudo chown shifa:shifa /opt/shifa/shifa-oms.jar

sudo rm -rf /var/www/shifa/admin
sudo mkdir -p /var/www/shifa/admin
sudo cp -r ~/admin-dist/* /var/www/shifa/admin/
sudo chown -R www-data:www-data /var/www/shifa/admin
Your repo already has a one-command helper (deploy\push-to-aws.ps1) that builds, uploads, backs up and restarts. Once this box is running you can reuse it for future updates by pointing -Ip <ELASTIC_IP> -KeyPath <your.pem>. For the very first setup, the manual steps above are clearest.

12. Start & verify

sudo systemctl start shifa-oms
sudo systemctl status shifa-oms --no-pager | head -6

# Watch it boot: Flyway migrates the empty DB, then Tomcat starts on 8080
sudo journalctl -u shifa-oms -f
# Look for: "Successfully applied N migrations", "Tomcat started on port 8080", "Started Application"

Quick checks (from the server):

curl -s -o /dev/null -w "%{http_code}\n" http://localhost/            # 200 (admin loads)
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/api/states  # 401 (API up + auth enforced)

Then open http://<ELASTIC_IP>/ in a browser. The app is live. First login uses the seeded admin (admin / admin123) — change this immediately (Users page) or run Step 14.

If it fails to start: the most common causes are a wrong DB_PASSWORD, a blank STORAGE_S3_BUCKET (with STORAGE_PROVIDER=S3 the app refuses to boot), or the IAM role not attached. The journal shows the exact reason.

13. (Optional) HTTPS with a domain

When the client points a domain (e.g. oms.theirdomain.com) at <ELASTIC_IP> (an A record):

sudo snap install --classic certbot
sudo ln -sf /snap/bin/certbot /usr/bin/certbot
sudo certbot --nginx -d oms.theirdomain.com     # auto-edits Nginx, adds the 443 block, auto-renews

Also set server_name oms.theirdomain.com; in the Nginx file. Certbot (Let’s Encrypt) is free.

14. Make it a clean handover (no demo / order data)

On a fresh DB, the migrations seed demo/test data (including sample orders) so the app is explorable. For a client hand-over you’ll want the catalog + settings kept but all demo orders/customers/leads removed, and your real staff (1 admin + the 2 team leads + 17 salespeople) seeded.

This is a one-time SQL script run after the app is up — it is not a code migration, so it can never affect the current live box. It:

  • deletes all orders, line items, payments, status history, receivables, courier shipments, returns, leads, customer notes/tags, notifications, audit log, insights and demo stock movements;
  • optionally clears demo suppliers / purchase orders / expenses;
  • resets the invoice & PO number sequences to 1;
  • keeps the 30-product catalog, delivery states, GST/company settings and WhatsApp templates;
  • replaces the demo logins with your real admin + 19 staff (correct names, emails, mobiles, team-lead assignments).
I’ll generate this exact handover-clean.sql for you once you confirm the final admin username/password and that the 19-person team sheet is final. You’ll run it once with a backup first: 
MYSQL_PWD=YOUR_DB_PASSWORD mysqldump --no-tablespaces -u shifa shifa_dashboard > ~/pre-clean-backup.sql
MYSQL_PWD=YOUR_DB_PASSWORD mysql -u shifa shifa_dashboard < handover-clean.sql

15. Capacity, cost guardrails & day-2 ops

Will t3.micro handle your load?

Yes. Your profile — ~20–25 salespeople logged in, each punching ~4–5 orders/day — is a read-mostly workload with very low write volume (well under a handful of concurrent INSERT/UPDATE/DELETE at peak). The connection pool is capped at 10 DB connections and the JVM heap is tuned for 1 GB, which comfortably covers dozens of concurrent logged-in users doing reads. The 2 GB swap absorbs occasional spikes. If usage ever grows a lot, moving to t3.small (2 GB) is a one-click resize (a small monthly cost, not free-tier).

Cost guardrails (stay free)

Set a Billing → Budgets alert (e.g. ₹100/month) in the new account so you’re emailed if anything unexpected starts costing money. Also check Billing → Free Tier usage occasionally.

Everyday operations

sudo systemctl restart shifa-oms          # restart backend
sudo journalctl -u shifa-oms -n 100 --no-pager   # recent logs
sudo systemctl reload nginx               # after editing the site file
# Manual DB backup:
MYSQL_PWD=YOUR_DB_PASSWORD mysqldump --no-tablespaces -u shifa shifa_dashboard > ~/backup-$(date +%F).sql

The current live box is safe

This is a different AWS account, instance, key and IP. Nothing in this guide touches the existing production server — it keeps running exactly as-is. Deploy tooling for the new box uses its own IP/key, so the two never cross over.
