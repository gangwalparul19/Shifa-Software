Reference to review existing usability gaps and new features, before any code changes. Written for the real team: ~25 users, ~20 of them salespeople with limited digital experience. Guiding principle: make the salesperson's daily path dead-simple; keep power features for Admin/Accountant.
Analysis only — nothing in the app has been changed. Each item notes rough value / effort / risk.

2. Current functionality (quick inventory)

  • Order lifecycle: Pending approval → Approved → Label generated → Packed → Handed to delivery → Courier assigned → Dispatched → In transit → Out for delivery → Delivered/COD collected/Closed (+ Rejected, Cancelled, RTO, Delivery failed, Courier lost).
  • Salesperson: New Order, Orders (own), Leads (+ due follow-ups), Customers (own), Products (read), My Profile.
  • Packing: work queues (to pack / awaiting handover / awaiting dispatch), barcode scan, label print, handover, dispatch.
  • Accountant: Reconciliation, Reports, Expenses, P&L, Returns, Customers.
  • Admin: the above + Approvals, Inventory, Suppliers, POs, Notifications, Announcements, Audit, Users, Salespeople, Insights, Analytics, Backups, Settings.
  • Platform: JWT/RBAC, S3 storage, nightly backup, WhatsApp/courier in MOCK, PWA + offline order capture, live SSE dashboard.

3. Usability "loop holes" (existing pain points)

3.1 Too much on screen for salespeople

A salesperson really needs only New Order, My Orders, My Leads. Everything else is noise.

Fix: a stripped-down Salesperson Home — one big "➕ New Order" button, a simple "My Orders" list (search by phone), a "My Leads" tile; hide the rest.

3.2 The New Order form is long and technical

Many fields at once; optional vs required unclear; developer-style errors (e.g. "amountReceived must be a DECIMAL(12,2) value").

Fix: a guided wizard (Customer → Items → Payment → Review), plain-language errors ("Enter the 6-digit PIN code"), optional fields clearly marked, large touch targets.

3.3 Language barrier

UI is English-only; many salespeople prefer Hindi / regional language.

Fix (high impact): a bilingual UI (English + Hindi) toggle for the salesperson screens. Likely the single biggest error-reducer.

3.4 Typing-heavy address entry → data errors

City/State/PIN typed by hand → typos, mismatches.

Fix: auto-fill City + State from the 6-digit PIN code. Big accuracy + speed win.

3.5 Too many statuses exposed

14+ statuses confuse a salesperson who just wants "where is my order?".

Fix: a simplified status tracker — Placed → Approved → Packed → Shipped → Delivered, with friendly icons.

3.6 Error & empty states

Fix: plain-language messages, "what to do next" hints, consistent primary-button placement.

3.7 Confirmation on important actions

Ensure cancel/reject/delete always confirm with a clear plain-language prompt (audit for gaps).

4. Client-requested features (detailed)

4.1 Multi-Label Print (Packaging)

Print labels for several orders at once in one PDF.

Good news: the backend already supports this (POST /api/admin/labels/internal/bulk). It's just not surfaced in the packing UI.

Work: add multi-select to the "to pack" queue + a "Print selected labels" button calling the existing endpoint.

Value: HighEffort: LowRisk: Low

4.2 Multi-Pack Option (Packaging)

One order shipped in multiple boxes — capture package count, produce a label per box ("Box 1 of 3").

Work: add packageCount (+ optional per-box weight/notes) to the order; render N labels; reflect in handover/dispatch + courier AWB. Needs a migration.

Value: Med-HighEffort: Med-HighRisk: Med

4.3 Handover popup with handover person's name

When the packer clicks Handover, a popup captures who it was handed to (courier/agency name, optional phone).

Today POST /api/packing/{id}/handover takes no data — no name is captured.

Work: add handoverName (+ optional phone) to the handover request; persist on the order/status-history; show on detail; add the popup in the packing UI.

Value: HighEffort: LowRisk: Low

4.4 New "Payment Verifier" role + Payment dashboard

A dedicated role that verifies each payment's authenticity (screenshot vs amount) and handles customer engagement, with a separate Payment dashboard. New salesperson orders surface here.

Work (significant):

  • New role PAYMENT_VERIFIER (enum + security + nav).
  • New step: order created → Payment verification (view screenshot, confirm amount, Verify/Reject + note) → Admin approval. Needs a new order status + state-machine transitions + notifications.
  • New Payment dashboard: verification queue, screenshot viewer, amount check, verify/reject, engagement notes, filters.
  • Admin dashboard: prominent live new-order alert (SSE already exists).
Design choice: verification before admin approval (blocking) is cleaner for authenticity control than a parallel check.
Value: HighEffort: HighRisk: Med-High (core workflow + 490+ tests)

4.5 Alternate contact number on the order page

Capture a second phone number (for failed-delivery contact). Only customerMobile exists today.

Work: add optional alternateMobile (10-digit) to the order-entry payload, entity (migration), New Order form, and detail view — mirrors the existing optional email field.

Value: MedEffort: LowRisk: Low

4.6 Round order price to the nearest rupee

₹2679.99 → ₹2680 (round the grand total).

Work: half-up rounding on the total, plus a visible "Round-off" line on the invoice (standard Indian practice) rather than silently changing the taxable value. Apply across total, invoice PDF, COD amount, reports.

Validate with the accountant — GST taxable base and invoice/Vyapar totals must reconcile.
Value: MedEffort: Low-MedRisk: Med (GST)

5. Additional suggestions

High-value additions

  • Bilingual English/Hindi UI — biggest error-reducer for this team (§3.3).
  • PIN-code auto-fill of city/state (§3.4).
  • Simplified Salesperson Home + status tracker (§3.1, §3.5).
  • Guided New Order wizard (§3.2).
  • Go live with WhatsApp order confirmations (currently MOCK) — fewer "where's my order?" calls.
  • Prominent risky-customer nudge at order entry (Customer-360 risk already exists).
  • Draft orders — save an incomplete order and finish later.
  • Packing slip printed with the label (item checklist).

Small quality-of-life fixes

  • Plain-language validation messages everywhere.
  • Bigger tap targets, fewer taps on the salesperson flow.
  • "Search order by phone" front-and-center for salespeople.
  • Consistent confirmation dialogs.

6. What to simplify or remove

  • Trim salesperson navigation to New Order, My Orders, My Leads, My Profile — nothing else visible.
  • Unused CUSTOMER role (leftover from the removed storefront) + dead storefront-era columns — consider cleanup. Low priority; via migration, don't drop columns casually.
  • Consolidate overlapping concepts (Leads vs Orders vs Customers) for salespeople — clearer naming/grouping so they aren't unsure where to go.
  • Reduce visible order statuses for non-admins (§3.5).
  • Keep advanced modules admin/accountant-only (Insights, Analytics, Suppliers, POs, Expenses, P&L) — verify salespeople never reach them.
⚠️ Don't delete DB columns/tables casually. Prefer hiding in the UI; if removing, use a new Flyway migration (V39+), never edit an applied one, and keep the 490+ tests green.

8. Risks & things to confirm before building

  • Rounding vs GST: round the total with a visible round-off line; don't distort the taxable base. Confirm invoice PDF + Vyapar export reconcile.
  • Payment-verification workflow changes the state machine + notifications — plan the new status and update tests deliberately.
  • Every schema change = a new Flyway migration (V39+); never edit an applied one.
  • Keep the 490+ test suite green.
  • Train the team — with 20 low-experience users, in-app help / a one-page guide per change matters as much as the code.

9. Next steps

  3. We batch the small additive ones (handover name, alternate contact, multi-label UI, round-off) into a single deploy.
