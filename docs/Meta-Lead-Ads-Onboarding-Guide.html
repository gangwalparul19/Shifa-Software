Meta Lead Ads → OMS: Integration & Onboarding Guide

A step-by-step playbook to connect your Facebook & Instagram lead ads to the OMS portal via a secure webhook — so every new lead lands in your portal automatically, de-duplicated and assigned to your team. Written for a setup with two Ads Manager accounts.

Audience: client + implementation team  ·  Webhook endpoint: https://shifa.weblithic.online/api/webhooks/meta/leads

The one thing to understand first

It shapes every step below.

Lead webhooks are delivered per Facebook Page, not per Ads Manager account. An Ads Manager runs the campaigns, but a lead form is attached to a Facebook Page, and Meta sends the notification to whichever Meta App that Page is subscribed to. So 2 Ads Managers really means "the Pages behind those two Ads Managers." Count the distinct Pages, not the ad accounts.

Also key: the webhook does not contain the lead's details — only a leadgen_id + page_id. We then call the Graph API with that Page's access token to fetch the real answers (name, phone, email). And Meta deletes lead data after 90 days, so retrieval must be automatic — which the webhook makes it.

  1. A Facebook / Instagram lead form is submitted.
  2. Meta sends a signed POST to /api/webhooks/meta/leads (carries leadgen_id + page_id).
  3. OMS verifies the signature, then calls Graph GET /{leadgen_id}?fields=field_data with the Page token.
  4. OMS creates a CRM lead (source Facebook / Instagram), de-dupes by mobile/email, assigns per rule, logs an activity.
  5. The lead appears in your OMS Leads list — no manual typing.

Who does what

  • Client provides the Meta assets (App, Pages, access) and clicks through their Business Manager — those assets belong to them.
  • We (implementation) provide the OMS webhook + build, and drive the client through the Meta clicks on a screen-share and capture the tokens.
Golden rule:  we never need the client's Facebook password. We need roles/access on the App and Pages, plus a few tokens/IDs — all collectable in one 30-minute screen-share.

2

Create / identify the Meta App

  1. Go to developers.facebook.com → My Apps → Create App → type Business (or reuse a Business app). Name it e.g. "Shifa OMS Leads".
  2. Settings → Basic: copy App ID, click Show to copy App Secret. Share with us securely. The App Secret signs the webhook — keep it private.
  3. Add Products: Webhooks + Facebook Login for Business (and Marketing API if prompted).
  4. Two-Business-Manager case repeat for the second BM's app — we store both App Secrets.
Capture now: APP_ID, APP_SECRET. We invent VERIFY_TOKEN = a 32+ character random string and keep it.
3

List the Pages and their IDs

We only care about Pages — leads attach to Pages.

GET https://graph.facebook.com/v21.0/me/accounts?access_token=USER_TOKEN
# -> returns every Page the logged-in admin manages: { id (Page ID), name, access_token }

Write down the Page ID of every page that runs lead ads across both Ads Managers. These Page IDs are the join key the OMS uses to pick the right token when a lead arrives.

Two Ads Managers: count distinct Pages, not ad accounts. If both Ads Managers advertise the same Pages, you still subscribe each Page only once.
4

Get the tokens (the part everyone trips on)

Two routes. Route A (System User) is production-grade and durable — recommended. Route B (long-lived Page token) is quick for a pilot. Do one of them per Page.

Common first move — a short-lived User token (Graph API Explorer)

  1. developers.facebook.com/tools/explorer → pick the App (top-right).
  2. Add Permissions: pages_show_list, pages_manage_metadata, pages_read_engagement, leads_retrieval, business_management.
  3. Generate Access Token → client approves the dialog. You now hold a short-lived User token (1–2 hrs) — enough to do Steps 3–6 on the call.

Exchange for a long-lived User token (≈60 days)

GET https://graph.facebook.com/v21.0/oauth/access_token
    ?grant_type=fb_exchange_token
    &client_id=APP_ID
    &client_secret=APP_SECRET
    &fb_exchange_token=SHORT_LIVED_USER_TOKEN
# -> access_token = long-lived USER token

Route A — System User token recommended

A System User belongs to the Business, not a person, so its token survives password changes / someone leaving.

  1. business.facebook.com → Business Settings → Users → System Users → Add → create one (role Admin/Employee). Two separate Business Managers → one System User each.
  2. Assign assets: assign each lead-ad Page to the System User with Manage/Full access.
  3. Generate token for the System User with the same permissions; set no-expiry / 60-day per policy.
  4. Call GET /me/accounts (or GET /{page_id}?fields=access_token) with it to get a Page access token per Page — these are what the OMS stores.

Route B — long-lived Page token (quick pilot)

  1. With the long-lived User token: GET /v21.0/me/accounts?access_token=LONG_LIVED_USER_TOKEN.
  2. For each Page, copy its access_token. A Page token from a long-lived user token has no expiry of its own — but dies if the admin revokes it / changes password / loses the Page role.
Verify every token: paste each into developers.facebook.com/tools/debug/accesstoken/ and confirm it is a Page (or System User) token, lists the right Page ID, has leads_retrieval, and shows the expiry you expect.
Hand to us per Page: PAGE_ID → PAGE_ACCESS_TOKEN (plus the System User token if Route A, so we can refresh later).
5

Point the webhook at the OMS

  1. App Dashboard → Webhooks → object Page → Subscribe to this object.
  2. Callback URL: https://shifa.weblithic.online/api/webhooks/meta/leads
  3. Verify Token: the VERIFY_TOKEN from Step 2 (must match the OMS config).
  4. Verify and Save. Meta GETs the callback with hub.mode=subscribe&hub.challenge=…&hub.verify_token=…; the OMS echoes the challenge when the token matches → subscription turns green. (Endpoint must be real HTTPS with a valid cert — ours is; Meta rejects self-signed.)
  5. In the Page webhook fields, tick leadgen (the Lead Ads event).
  6. Two apps repeat for the second app — same callback URL.
6

Subscribe EACH Page to the App

Easy to miss: ticking leadgen on the app is not enough — every Page must be individually subscribed, or that page's leads never arrive.

For each Page ID from Step 3 (with that Page's token):

POST https://graph.facebook.com/v21.0/{PAGE_ID}/subscribed_apps
     ?subscribed_fields=leadgen
     &access_token={PAGE_ACCESS_TOKEN}
# -> {"success": true}

# confirm:
GET https://graph.facebook.com/v21.0/{PAGE_ID}/subscribed_apps?access_token={PAGE_ACCESS_TOKEN}

The OMS will also expose POST /api/admin/meta/subscribe-page?pageId= to do this from inside the portal once the Page token is stored. Either way, do it once per Page.

7

Store everything in the OMS

Give us these; we set them in the prod server environment (never committed to code):

META_LEADS_ENABLED=true
META_LEADS_VERIFY_TOKEN=<the string from Step 2>
META_GRAPH_VERSION=v21.0

# App 1 (Business Manager 1)
META_APP1_ID=<app id>
META_APP1_SECRET=<app secret>

# App 2 (only if two separate Business Managers)
META_APP2_ID=<app id>
META_APP2_SECRET=<app secret>

# Page tokens — one line per Page, across BOTH Ads Managers
META_PAGE_TOKEN_<PAGE_ID>=<page access token>
Blank values no-op safely — a half-configured setup never breaks the rest of the OMS.
8

Test end-to-end — zero ad spend

  1. developers.facebook.com/tools/lead-ads-testing → pick the Page + a lead form → Create Lead.
  2. Meta fires a real leadgen webhook → OMS verifies the signature → fetches the lead → creates a CRM lead, de-dupes, assigns, logs an activity.
  3. Open the OMS Leads list → the test lead appears. Delete the test lead afterward.
  4. Repeat for one Page from each Ads Manager so both are proven.
9

Go live / App Review

  • To receive leads from Pages not owned by the app's admins (real production), the app needs Advanced Access for leads_retrieval + the pages permissions via App Review (screencast + use-case). Start this early — it's the usual bottleneck.
  • Until approved, the Lead Ads Testing Tool and Pages/users with an app role work in Development mode — enough to validate the whole chain.

The exact Graph calls, in order

# 1. Short-lived user token: Graph API Explorer (UI) with the 5 permissions.

# 2. Long-lived user token
GET /v21.0/oauth/access_token?grant_type=fb_exchange_token&client_id=APP_ID&client_secret=APP_SECRET&fb_exchange_token=SHORT_USER_TOKEN

# 3. Page tokens (one per page)
GET /v21.0/me/accounts?access_token=LONG_USER_TOKEN            # -> [{id, name, access_token}, ...]

# 4. Subscribe each page to the app
POST /v21.0/{PAGE_ID}/subscribed_apps?subscribed_fields=leadgen&access_token=PAGE_TOKEN

# 5. (When a webhook arrives) fetch the lead
GET /v21.0/{LEADGEN_ID}?fields=field_data,created_time,ad_id,form_id,platform&access_token=PAGE_TOKEN
#   field_data = [{name:"full_name",values:["..."]},{name:"phone_number",values:["..."]},{name:"email",...}]

# 6. Verify any token: developers.facebook.com/tools/debug/accesstoken/

What the webhook body looks like

{
  "object": "page",
  "entry": [{
    "id": "<PAGE_ID>",
    "time": 1734567890,
    "changes": [{
      "field": "leadgen",
      "value": {
        "leadgen_id": "1234567890",
        "page_id": "<PAGE_ID>",
        "form_id": "9876543210",
        "created_time": 1734567889,
        "ad_id": "...", "adgroup_id": "..."
      }
    }]
  }]
}

The OMS verifies X-Hub-Signature-256 (hex HMAC-SHA256 of the raw body, keyed by the matching App Secret), then for each changes[].value fetches the lead by leadgen_id using the token stored for page_id.

Handling the TWO Ads Managers

SituationWhat to do
Both Pages under ONE Business Manager / one app (recommended)One app, one App Secret, one verify token, one callback URL. Subscribe every Page (from both Ads Managers) to the app and store each Page's token. The OMS routes by page_id automatically.
Two separate Business Managers → two appsTwo app entries (two App Secrets). Same single callback URL; the OMS signature check tries each App Secret and page_id disambiguates. Store each Page's token regardless of app.
Both Ads Managers advertise the SAME PagesEven simpler — subscribe each Page once; the driving ad account is captured as context on the Graph response if attribution is wanted.
Rule of thumb: count the distinct Facebook Pages across both Ads Managers, not the Ads Managers. Each distinct Page needs (1) to be subscribed to our app for leadgen, and (2) a stored Page access token in the OMS.

One-paragraph summary to send the client

We'll connect your lead ads to your OMS via a secure webhook. On a short screen-share we'll (1) create/pick a Meta App and copy its App ID + Secret, (2) list the Facebook Pages that run your lead ads across both Ads Managers, (3) generate a durable access token for each Page (ideally via a Business "System User"), (4) point Meta's webhook at https://shifa.weblithic.online/api/webhooks/meta/leads and subscribe each Page to the leadgen event, and (5) fire a test lead with Meta's free testing tool to confirm it lands in your portal. After that, every new Facebook/Instagram lead flows into your OMS automatically, de-duplicated and assigned to your team — no manual re-typing.
