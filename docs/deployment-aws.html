Deploy Shifa OMS to AWS — EC2 + RDS

App server (EC2) + managed database (RDS MySQL) · dashboard-only app · buffered for 50 concurrent users · stays in the free tier / credits

What this build is. The app runs on an EC2 server; the database runs on Amazon RDS (managed MySQL, auto-backed-up). Splitting them gives each its own memory and a comfortable buffer for ~50 concurrent users — no connection or loading stalls. It stays inside the free tier for the first year (EC2 t4g.small free until 31 Dec 2026; RDS free for 12 months) with your $100–$200 credits covering the rest. New to AWS? The click-by-click beginner version is aws-free-tier-guide.html.

1 Account, region & budget alarm

Sign up at aws.amazon.com/free; set the region to Asia Pacific (Mumbai) ap-south-1 and keep it. Before creating anything, turn on spending protection: Billing → Budgets → Create budget → "Zero spend budget" (your email), and Billing → Preferences → Free Tier alerts. Choose the Paid Plan at signup (you still get the credits, plus the 12-month RDS free allowance); the budget alarm keeps you safe.

2 Create the database (RDS for MySQL)

Console → RDS → Create database → Standard create → MySQL 8.

Instance sizerecommended db.t4g.small (2 GB) for a firm 50-user buffer — or db.t4g.micro (1 GB) to stay strictly freeSee the buffer math in Step 13. small supports ~170 connections vs ~85 on micro.
Storage20 GB gp3, autoscaling offgp3 gives steady IOPS; off = can't silently grow past free.

Free vs buffered. db.t4g.micro is free for 12 months and handles 50 light users with the pool tuned (Step 13). If you want a guaranteed cushion so busy bursts never cause connection/loading issues, use db.t4g.small (one size up, ~₹2,400/mo — not free). Either way it's a one-click resize later with no app change. Do not enable Multi-AZ (paid) unless you need HA.

When status = Available, copy the Endpoint (e.g. shifa-mysql.xxxx.ap-south-1.rds.amazonaws.com) — used in Step 8.

After it's Running, allocate an Elastic IP (EC2 → Elastic IPs → Allocate → Associate to shifa-app) for a stable address.

4 Let EC2 reach RDS (private)

  1. RDS → shifa-mysql → Connectivity & security → VPC security groups → open the DB's security group.
  2. Inbound rules → Edit → Add rule: type MySQL/Aurora (3306), Source = the EC2's security group. Save.
This privately allows only the app server to talk to the database on port 3306 — the DB is never exposed to the internet.

sudo apt update && sudo apt -y upgrade
sudo apt -y install openjdk-21-jdk nginx mysql-client git unzip

Install the MySQL client only (to talk to RDS) — not mysql-server, since the database lives on RDS. Don't build Angular on this box (build on your PC, Step 9).

7 Create the database & user on RDS

mysql -h <RDS_ENDPOINT> -u admin -p
CREATE DATABASE IF NOT EXISTS shifa_dashboard CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER IF NOT EXISTS 'shifa'@'%' IDENTIFIED BY 'CHANGE_ME_STRONG_DB_PASSWORD';
GRANT ALL PRIVILEGES ON shifa_dashboard.* TO 'shifa'@'%';
FLUSH PRIVILEGES;
EXIT;

Flyway builds all tables (V1…V27, incl. the demo/test seed) automatically on first backend start — no manual schema work.

sudo tee /etc/nginx/sites-available/shifa >/dev/null <<'NGINX'

    listen 80;
    server_name _;                 # replace with your hostname
    client_max_body_size 15m;
    gzip on; gzip_types text/css application/javascript application/json image/svg+xml; gzip_min_length 1024;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;

        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Connection '';
        proxy_buffering off; proxy_cache off; proxy_read_timeout 3600s;

    location / {

        try_files $uri $uri/ /index.html;
    }
}
NGINX

13 Buffer & scaling for 50 concurrent users headroom

"50 concurrent" isn't 50 queries at one instant — each click is a query lasting tens of milliseconds. The buffer comes from three sized-with-headroom layers:

LayerSettingHeadroom / math
DB connection pool (app)DB_POOL_SIZE=2525 reusable connections × ~10 queries/sec each ≈ 250 queries/sec capacity — far above what 50 clicking users generate.
Database (RDS)db.t4g.small (2 GB)Supports ~170 connections; a 25-connection pool uses ~15% → big cushion (and room for a 2nd app node later). db.t4g.micro ≈ 85 connections — still fine at pool 20, less cushion.
App server (EC2)t4g.small 2 GB, -Xmx1300m (or t4g.medium 4 GB, -Xmx2500m)DB offloaded to RDS, so the JVM owns the box. Nginx serves thousands of connections; 50 users is trivial. t4g.medium adds burst headroom.
To make "never any connection/loading issues" a guarantee: use db.t4g.small + DB_POOL_SIZE=25 (optionally t4g.medium app). This leaves ~85% DB-connection headroom and comfortable RAM/CPU margin at 50 concurrent users.

Watch it (free, RDS → Monitoring)

  • DB Connections — should sit well under the max (pool caps it at 25). CPU & Freeable Memory — should have margin during busy hours.
  • If any of these run hot, resize the DB one notch (small → medium) — a few-minutes, one-click change, no app edit.
  • Data growing to millions of rows is fine — MySQL 8 handles it with the existing indexes; watch RAM/connections, not row count.
Future scale (optional): if you later add Lambda functions that hit the DB, or a 2nd app node, put RDS Proxy in front of RDS to pool/limit connections centrally. Not needed for one app node + HikariCP.

14 Backups

  • RDS automated backups (7 days) are on — daily snapshots + point-in-time restore. Test a restore once so you trust it.
  • Take a manual snapshot (RDS → Actions → Take snapshot) before big changes.
  • The app's nightly dump writes to the EC2 disk; RDS backups are the primary safety net.

15 Daily 8 AM consolidated report to the admin (Lambda)

Every day at 8:00 AM IST the admin gets an emailed consolidated report of the previous day — total sales, a per-salesperson breakdown, customers, and the order-status split. The report + email are built inside the app (endpoint POST /api/admin/reports/daily-digest/run); a tiny Lambda just triggers it on schedule. Two ways to run it:

Option A — App's built-in scheduler (simplest, no Lambda)

The backend already sends this report on a schedule. Just set these in /etc/shifa/shifa.env and restart:

MAIL_MODE=SMTP                 # real email (see mail settings below)
REPORT_DIGEST_TO=admin@yourcompany.com
REPORT_DIGEST_CRON=0 0 8 * * *  # 8:00 AM server time (set the server timezone to IST)
REPORT_DIGEST_ENABLED=true

Set the server clock to IST once: sudo timedatectl set-timezone Asia/Kolkata, then sudo systemctl restart shifa-oms. Done — no Lambda needed.

Option B — AWS Lambda triggers it at 8 AM IST (what you asked for)

Use this if you prefer the schedule to live in AWS. Turn OFF the internal scheduler so the report isn't sent twice:

# in /etc/shifa/shifa.env
REPORT_DIGEST_ENABLED=false
MAIL_MODE=SMTP
REPORT_DIGEST_TO=admin@yourcompany.com
  1. Lambda → Create function → Python 3.12 → name shifa-daily-report. Set env vars APP_BASE (your https://your-site), ADMIN_USER, ADMIN_PASS. Paste:
import os, json, urllib.request
def handler(event, context):
    base = os.environ['APP_BASE'].rstrip('/')
    # 1) log in as admin to get a token
    login = urllib.request.Request(base + '/api/auth/login',
        data=json.dumps({'username': os.environ['ADMIN_USER'],
                         'password': os.environ['ADMIN_PASS']}).encode(),
        headers={'Content-Type': 'application/json'}, method='POST')
    token = json.loads(urllib.request.urlopen(login, timeout=20).read())['accessToken']
    # 2) trigger yesterday's consolidated report email
    run = urllib.request.Request(base + '/api/admin/reports/daily-digest/run',
        headers={'Authorization': 'Bearer ' + token}, method='POST')
    return urllib.request.urlopen(run, timeout=60).read().decode()
  1. Set the handler to lambda_function.handler; increase timeout to ~30s.
  2. Add trigger → EventBridge → Create new rule → Schedule expression: cron(30 2 * * ? *) — that's 02:30 UTC = 08:00 IST, daily.
  3. Test once (Lambda → Test) and confirm the admin receives the email.
The login response field is accessToken (adjust if your build differs). Keep ADMIN_PASS in the Lambda env (or better, in AWS Secrets Manager). Because the app builds the report, the Lambda stays tiny and needs no database access.
Don't run both options — pick A or B, otherwise the admin gets two emails. (Option B sets REPORT_DIGEST_ENABLED=false to prevent that.)

Also useful — weekly RDS snapshot Lambda (optional, ≈ ₹0)

# Lambda (Python 3.12), trigger: EventBridge schedule rate(7 days)
import boto3, datetime
rds = boto3.client('rds')
def handler(event, context):
    stamp = datetime.datetime.utcnow().strftime('%Y-%m-%d-%H%M')
    rds.create_db_snapshot(DBInstanceIdentifier='shifa-mysql',
                           DBSnapshotIdentifier=f'shifa-weekly-{stamp}')
    return 'ok'

Give its role rds:CreateDBSnapshot. Lambda's always-free tier makes these schedules cost ≈ ₹0. Beginner steps: aws-free-tier-guide.html → Part D.

16 Redeploys & zero-downtime upgrade

Rebuild on PC (Step 9), scp up, then on the server:

sudo cp ~/shifa-oms.jar /opt/shifa/shifa-oms.jar && sudo chown shifa:shifa /opt/shifa/shifa-oms.jar
sudo rm -rf /var/www/shifa/admin/* && sudo cp -r ~/admin-dist/* /var/www/shifa/admin/
sudo systemctl restart shifa-oms && sudo systemctl reload nginx
Single-server reality: with one EC2, an app restart pauses the site ~30–60 s. Data is safe (it's on RDS). For internal use by 50 staff this is usually fine. True zero-downtime = add a 2nd EC2 + an Application Load Balancer (~₹1,700/mo) and deploy one node at a time; optionally switch RDS to Multi-AZ. Same jar, same RDS — no app change.
Never re-import a DB dump over live data. Add a new Flyway migration (V28__*.sql, …) — it applies on the next backend restart. Never edit an applied migration.
