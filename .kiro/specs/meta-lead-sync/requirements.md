# Requirements Document

## Introduction

Meta Lead Sync integrates the business's Meta (Facebook/Instagram) Lead Ads campaigns into Shifa OMS so that a lead submitted on the business Page's Instant Form is captured into the application's `leads` pipeline automatically, with no manual data entry.

The integration uses Meta's "notify then fetch" model. Meta delivers a lightweight webhook notification (a `leadgen` change event carrying `leadgen_id`, `form_id`, and `page_id`) to a public application endpoint. The application then calls the Meta Graph API to fetch the full lead field data, normalizes and maps it, and persists it through the existing `LeadService.capture` path. Auto-imported leads are assigned to a dedicated "Meta Leads" system user so an admin or salesperson can review the pool and pick leads up.

The feature reuses existing Shifa OMS infrastructure: the public `/api/webhooks/**` security allowance, the transactional outbox pattern for reliable out-of-band processing, the `leads`/`lead_status_history` schema, the `LeadSource` enum, Flyway versioned migrations, and externalized secrets in `local-secrets.properties` / production environment variables.

This document also captures an operational connectivity/access-test capability so the Page Access Token and Page ID can be verified against the Graph API before relying on live webhooks, and support for Meta's Lead Ads Testing Tool test leads flowing end-to-end into a real lead row.

## Glossary

- **Meta**: Facebook/Instagram advertising platform operated by Meta Platforms, which sends Lead Ads notifications and serves lead data via the Graph API.
- **Lead Ads Instant Form**: A Meta-hosted form attached to an ad on a business Page; a submission produces a lead record on Meta.
- **Graph API**: Meta's HTTP API used to fetch full lead field data by lead identifier.
- **Meta_Webhook_Endpoint**: The application HTTP component that handles Meta's webhook verification handshake (GET) and lead notifications (POST) under `/api/webhooks/meta`.
- **Meta_Lead_Ingest_Service**: The application service that records the raw notification, enforces idempotency, fetches lead data via the Graph API, maps fields, and persists the lead.
- **Meta_Graph_Client**: The application component that performs outbound Graph API calls (fetch lead field data, connectivity test) using the Page Access Token.
- **Meta_Lead_Ingest_Drainer**: The outbox consumer that processes queued Meta lead ingest events out-of-band, including retries for transient failures.
- **Meta_Connectivity_Tester**: The admin-triggerable component that verifies the configured Page Access Token and Page ID against the Graph API.
- **LeadService**: The existing application service whose `capture` method persists a new lead with a starting status of NEW and a status-history row.
- **LeadSource**: The existing enum of lead origin channels (WHATSAPP, INSTAGRAM, FACEBOOK, GOOGLE, OFFLINE, OTHER).
- **Meta_Leads_System_User**: A dedicated non-login application user account that owns auto-imported Meta leads until a human picks them up.
- **leadgen_id**: The Meta identifier of a single Lead Ads submission, supplied in the webhook notification and used to fetch field data from the Graph API.
- **form_id**: The Meta identifier of the Instant Form that produced the lead.
- **page_id**: The Meta identifier of the business Page that owns the ad and form.
- **Verify_Token**: A shared secret generated by the application owner, used only during the webhook subscription verification handshake.
- **App_Secret**: The Meta App secret used to compute the HMAC-SHA256 signature that validates webhook authenticity.
- **Page_Access_Token**: The long-lived Meta access token (system-user preferred) used to authenticate Graph API calls for the configured Page.
- **X-Hub-Signature-256**: The HTTP header Meta sends on webhook POST requests, containing the HMAC-SHA256 digest of the raw request body keyed by the App_Secret.
- **Ingest_Record**: The persisted row that stores a received Meta notification (including `leadgen_id`, raw payload, and processing state) for idempotency and retry.
- **System**: The Shifa OMS backend application as a whole.

## Requirements

### Requirement 1: Webhook Subscription Verification Handshake

**User Story:** As an integration administrator, I want the application to answer Meta's subscription verification challenge, so that Meta accepts the webhook endpoint and begins delivering lead notifications.

#### Acceptance Criteria

1. WHEN a GET request is received at `/api/webhooks/meta` with query parameters `hub.mode` equal to `subscribe`, `hub.verify_token` equal to the configured Verify_Token, and a `hub.challenge` value, THE Meta_Webhook_Endpoint SHALL respond with HTTP 200 and a body containing exactly the received `hub.challenge` value.
2. IF a GET request is received at `/api/webhooks/meta` with a `hub.verify_token` that does not equal the configured Verify_Token, THEN THE Meta_Webhook_Endpoint SHALL respond with HTTP 403 and SHALL NOT echo the challenge.
3. IF a GET request is received at `/api/webhooks/meta` that omits `hub.mode`, `hub.verify_token`, or `hub.challenge`, THEN THE Meta_Webhook_Endpoint SHALL respond with HTTP 400.
4. THE Meta_Webhook_Endpoint SHALL permit the GET verification request without prior authentication.

### Requirement 2: Webhook Authenticity Verification

**User Story:** As a security-conscious operator, I want inbound lead notifications validated against the App Secret, so that forged requests are rejected before any lead is created.

#### Acceptance Criteria

1. WHEN a POST request is received at `/api/webhooks/meta`, THE Meta_Webhook_Endpoint SHALL compute an HMAC-SHA256 digest of the exact raw request body using the configured App_Secret and compare it to the value in the `X-Hub-Signature-256` header.
2. IF the `X-Hub-Signature-256` header is absent on a POST request to `/api/webhooks/meta`, THEN THE Meta_Webhook_Endpoint SHALL respond with HTTP 401 and SHALL NOT create a lead.
3. IF the computed HMAC-SHA256 digest does not match the value in the `X-Hub-Signature-256` header, THEN THE Meta_Webhook_Endpoint SHALL respond with HTTP 401 and SHALL NOT create a lead.
4. WHEN the computed HMAC-SHA256 digest matches the value in the `X-Hub-Signature-256` header, THE Meta_Webhook_Endpoint SHALL accept the request for processing.
5. THE Meta_Webhook_Endpoint SHALL compare the computed and received signatures using a constant-time comparison.

### Requirement 3: Webhook Notification Receipt and Acknowledgment

**User Story:** As an integration administrator, I want the endpoint to store each notification and acknowledge Meta immediately, so that Meta does not disable the subscription and no notification is lost.

#### Acceptance Criteria

1. WHEN an authenticity-verified POST notification containing one or more `leadgen` change entries is received, THE Meta_Lead_Ingest_Service SHALL persist an Ingest_Record for each entry containing the `leadgen_id`, `form_id`, `page_id`, and the raw payload before responding.
2. WHEN an Ingest_Record has been persisted for every `leadgen` entry in a verified notification, THE Meta_Webhook_Endpoint SHALL respond with HTTP 200.
3. THE Meta_Lead_Ingest_Service SHALL persist each Ingest_Record and its corresponding outbox ingest event within a single database transaction.
4. WHERE a verified notification contains a change entry whose field is not `leadgen`, THE Meta_Lead_Ingest_Service SHALL ignore that entry and SHALL respond with HTTP 200 for the notification.
5. IF persisting the Ingest_Record fails, THEN THE Meta_Webhook_Endpoint SHALL respond with an HTTP 500 status so that Meta retries delivery.

### Requirement 4: Idempotent Lead Ingestion

**User Story:** As an integration administrator, I want duplicate notifications for the same lead to be ignored, so that Meta's retries never create duplicate lead records.

#### Acceptance Criteria

1. THE Meta_Lead_Ingest_Service SHALL treat `leadgen_id` as the unique idempotency key for a Meta lead.
2. WHEN a notification is received whose `leadgen_id` matches an existing Ingest_Record, THE Meta_Lead_Ingest_Service SHALL respond with HTTP 200 and SHALL NOT create an additional lead.
3. WHEN Meta lead ingestion for a given `leadgen_id` completes successfully, THE Meta_Lead_Ingest_Service SHALL persist the resulting lead identifier on the corresponding Ingest_Record.
4. FOR ANY `leadgen_id`, THE Meta_Lead_Ingest_Service SHALL create at most one lead record.

### Requirement 5: Fetch Lead Field Data from the Graph API

**User Story:** As an integration administrator, I want the application to fetch the full lead data from Meta, so that the stored lead contains the customer's submitted details.

#### Acceptance Criteria

1. WHEN an Ingest_Record is processed, THE Meta_Graph_Client SHALL request the lead field data from the Graph API at `GET /{leadgen_id}` authenticated with the configured Page_Access_Token.
2. WHEN the Graph API returns lead field data, THE Meta_Lead_Ingest_Service SHALL extract the `field_data` entries for later mapping.
3. IF the Graph API responds with a transient failure, including HTTP 429 and HTTP 5xx responses and network timeouts, THEN THE Meta_Lead_Ingest_Drainer SHALL retain the Ingest_Record in a retryable state.
4. IF the Graph API responds with an authorization failure indicating an invalid or expired Page_Access_Token, THEN THE Meta_Lead_Ingest_Service SHALL mark the Ingest_Record failed and SHALL record an administrator notification.
5. WHERE the Graph API request exceeds 10 seconds without a response, THE Meta_Graph_Client SHALL abort the request and treat the outcome as a transient failure.

### Requirement 6: Map and Normalize Lead Fields

**User Story:** As a salesperson, I want Meta lead fields mapped to the application's lead fields with a valid phone number, so that captured leads are complete and consistent with manually entered leads.

#### Acceptance Criteria

1. WHEN Graph API `field_data` is mapped, THE Meta_Lead_Ingest_Service SHALL set the lead customer name from the submitted full-name field.
2. WHEN the submitted phone number includes a country code, THE Meta_Lead_Ingest_Service SHALL normalize the phone number to its final 10 digits before capture.
3. IF a submitted phone number cannot be normalized to exactly 10 digits, THEN THE Meta_Lead_Ingest_Service SHALL capture the lead without a customer mobile and SHALL record the original submitted phone value in the lead note.
4. WHEN Graph API `field_data` contains an email field, THE Meta_Lead_Ingest_Service SHALL set the lead customer email from that value.
5. WHERE Graph API `field_data` contains custom question fields, THE Meta_Lead_Ingest_Service SHALL record the custom question labels and answers in the lead note within the 1000-character note limit.
6. IF the submitted full-name field is absent or blank, THEN THE Meta_Lead_Ingest_Service SHALL set the lead customer name to a defined placeholder value so that capture succeeds.

### Requirement 7: Persist the Lead Through the Lead Module

**User Story:** As a salesperson, I want imported Meta leads to appear in the lead pipeline as NEW, so that I can review and act on them using existing lead workflows.

#### Acceptance Criteria

1. WHEN a Meta lead is captured, THE Meta_Lead_Ingest_Service SHALL persist it through `LeadService.capture` so that the lead starts at status NEW with one status-history row.
2. WHEN a Meta lead is captured, THE Meta_Lead_Ingest_Service SHALL set the lead owner to the Meta_Leads_System_User.
3. WHEN a Meta lead is captured, THE Meta_Lead_Ingest_Service SHALL set the LeadSource to FACEBOOK.
4. WHEN a Meta lead is captured, THE Meta_Lead_Ingest_Service SHALL set the lead source note to a value containing the campaign or form name within the 200-character source-note limit.
5. IF `LeadService.capture` rejects the mapped lead with a validation error, THEN THE Meta_Lead_Ingest_Service SHALL mark the Ingest_Record failed and SHALL record an administrator notification.

### Requirement 8: Reliable Out-of-Band Processing and Retry

**User Story:** As an integration administrator, I want lead fetching and persistence to run out-of-band with retries, so that transient Meta failures are recovered without losing leads or blocking the webhook response.

#### Acceptance Criteria

1. WHEN an Ingest_Record and its outbox ingest event are committed, THE Meta_Lead_Ingest_Drainer SHALL process the ingest event asynchronously from the webhook response.
2. WHILE an Ingest_Record has an outstanding transient failure and its retry attempts are below the configured maximum, THE Meta_Lead_Ingest_Drainer SHALL schedule a subsequent retry using increasing backoff.
3. WHEN the configured maximum retry attempts for an Ingest_Record are exhausted, THE Meta_Lead_Ingest_Drainer SHALL mark the ingest event FAILED and SHALL record an administrator notification.
4. WHEN Meta lead ingestion completes successfully for an Ingest_Record, THE Meta_Lead_Ingest_Drainer SHALL mark the ingest event SENT.

### Requirement 9: Configuration and Secrets Management

**User Story:** As an integration administrator, I want Meta credentials and identifiers configured outside source control, so that secrets are protected and environment-specific values can differ between local and production.

#### Acceptance Criteria

1. THE System SHALL read the App_Secret, Page_Access_Token, Verify_Token, and Page_Id from externalized configuration rather than from committed source files.
2. WHERE a Page_Id is present in configuration, THE System SHALL use the configured Page_Id value; otherwise THE System SHALL fall back to the local default value 105357624712950.
3. IF the App_Secret, Page_Access_Token, or Verify_Token is missing at startup, THEN THE System SHALL log a warning identifying the missing configuration key by name.
4. THE System SHALL exclude the App_Secret, Page_Access_Token, and Verify_Token values from application log output.

### Requirement 10: Connectivity and Access Test

**User Story:** As an integration administrator, I want to verify the Page Access Token and Page ID against the Graph API on demand, so that I can confirm the integration is configured correctly before relying on live webhooks.

#### Acceptance Criteria

1. WHEN an administrator triggers the connectivity test, THE Meta_Connectivity_Tester SHALL call the Graph API for the configured Page_Id using the configured Page_Access_Token and SHALL return a success result including the Page name.
2. IF the connectivity test call fails authorization, THEN THE Meta_Connectivity_Tester SHALL return a failure result containing the Graph API error description.
3. THE connectivity test endpoint SHALL require an authenticated user with the ADMIN role.
4. THE Meta_Connectivity_Tester SHALL exclude the Page_Access_Token value from its returned result.

### Requirement 11: Test Lead Support

**User Story:** As an integration administrator, I want test leads from Meta's Lead Ads Testing Tool to flow through end to end, so that I can validate the full pipeline before launching the campaign.

#### Acceptance Criteria

1. WHEN a notification produced by Meta's Lead Ads Testing Tool is received and verified, THE Meta_Lead_Ingest_Service SHALL process it through the same fetch, map, and capture path as a production lead.
2. WHEN a test lead is captured, THE Meta_Lead_Ingest_Service SHALL persist a lead record owned by the Meta_Leads_System_User.

### Requirement 12: Schema and System User Provisioning

**User Story:** As a developer, I want the ingest table and the Meta Leads system user created by a versioned migration, so that the integration deploys consistently without editing applied migrations.

#### Acceptance Criteria

1. THE System SHALL create the Ingest_Record table through a new Flyway migration versioned above V48.
2. THE Ingest_Record table SHALL enforce a unique constraint on `leadgen_id`.
3. THE System SHALL create the Meta_Leads_System_User through a new Flyway migration.
4. THE Meta_Leads_System_User SHALL be provisioned with no usable login password.
5. THE new Flyway migrations SHALL be additive and SHALL NOT modify any previously applied migration.
